# Cloud deployment behind the private Site

Current consolidated entry point: `python -B -m prototypes.backend`. The Dockerfile now includes screen/lab and prepared-source mixed-language job routes. See [the frontend API handoff](../../docs/handoffs/frontend-api.md). This package is locally tested only; no Python host/bridge activation is claimed. Apply the prepared `deploy/sites/python-proxy.js` helper before a future rollout: it preserves mandatory job Idempotency-Key. Text/TTS currently require GEMINI_API_KEY even when screen analysis uses GEMINI_API_KEYS.

The user requires an accessible cloud URL. Sites runs Worker ESM, not our native Python/FastAPI process. Keep the private Site as the signed-in HTTPS entry point and deploy this Python app on a container/Python host such as Render. Users do not need the repo or a local Python installation.

Build from the repository root with `deploy/fastapi/Dockerfile`. The service uses the host's `PORT` (default 10000), binds 0.0.0.0 and reads writable `KIKI_DATA_DIR` (default /var/data/kiki). Run **one process and one instance**, with a persistent volume at /var/data if progress must survive service replacement. The SQLite journal and latest-frame memory require that single-instance boundary. Do not claim durability on an ephemeral filesystem or use a multi-instance deployment.

Server secrets: `GEMINI_API_KEY` and a newly generated `KIKI_PROXY_SECRET` of at least 32 characters. Do not put either in source, shell arguments, client scripts, screenshots or chat. `KIKI_REQUIRE_PROXY=1` makes startup fail if the proxy secret is missing. `/health` is the only public data-free probe. HTTP/WebSocket session access requires the matching proxy secret and Site-authenticated owner header.

The Site's runtime configuration uses `KIKI_FASTAPI_ORIGIN` (the verified root HTTPS origin) and the same `KIKI_PROXY_SECRET`. Its edge adapter checks the signed-in Site identity and same-origin browser mutations, strips incoming proxy credentials/identity, attaches trusted owner/key headers, forwards to a fixed verified origin without following redirects, and proxies HTTP/WebSocket responses. It contains no Python analysis/progress rules. Incoming Origin is checked at the Site and rewritten to the backend origin for the FastAPI same-origin guard.

`/mcp` is proxied too, preserving the existing three read tools. Python checks ownership for every data-bearing read; discovery returns no private data. This allows the chat to read Python-backed sessions once the cloud coupling is verified. Earlier Worker/D1 sessions remain in that store and are not silently imported into the new Python schema.

Rollout: deploy Python first, verify health and authenticated HTTP/WebSocket/owner isolation, then enable the Site proxy configuration. No unreachable backend or secret goes into the published page. Missing Python-origin configuration retains the current Worker demo. A configured but failing Python origin returns a visible failure; never silently fork progress by falling back to the Worker. Removing both proxy settings restores the old demo as an explicit rollback, without deleting either store.

Current status: source and proxy checks can run locally. Render was discovered and offered through the supported connection flow; deployment cannot be claimed before its account is connected and a service deployment succeeds. Persistent storage/service pricing must be checked against the selected account before provisioning a billed plan. This package has not created a Render resource or incurred hosting charges.
