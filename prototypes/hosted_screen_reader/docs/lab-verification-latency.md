# Lab verification latency

14 October 2026. The user confirms that recognition, progress and the clearer procedure work, and asks to optimize the slow verification loop. TOON and incremental important-field delivery are proposed options, not required replacements. Browser Gemma remains deferred.

## Baseline and shipped change

Recent production check requests took 6,487–7,968 ms (five successful sampled invocations; one additional 409 was discarded) with 22–24 ms Worker CPU. The browser used a twelve-second start interval and the backend a ten-second floor. Two distinct matching observations are required for support, so that schedule adds delay on top of model work. This is a sample of available production logs, not an exhaustive latency distribution.

The browser now uses a three-second minimum start interval when the frame/checkpoint changes, when a second criterion/action reading is pending, or when existing support needs renewal. Stable supported frames are skipped; unchanged failed/waiting states use the existing twelve-second idle interval. Provider retry deadlines and one-in-flight guards take precedence. The hosted server and Python lab service admit starts at three seconds, retaining provider quota handling, fresh pixel provenance, expiry and the two-distinct-frame rule. Faster cadence can increase RPM/TPM; shared-project cooldowns and key-rotation rules still apply. No latency SLA or promise of more quota is made.

The hosted client no longer fetches a redundant session refresh before every check: the Worker already loads/adopts the owned current state at admission. Revision refresh remains for Python's revision-bearing check request and for explicit context mutations. Stale-frame/context 409s can retry a fresh view without an artificial ten-second penalty. Hosted in-flight checks return a short, explicit 429 without starting another model request, reducing concurrent invalidation. Discarded stale/expired checks release the checking latch without adopting their findings. Genuine provider waits keep their full deadlines. The pure cadence helper is tested separately and served as a module with the lab script.

Runtime last_analysis_timing records total check time, provider time, received-frame-to-result age and provider output-token count when available. Values are runtime/provider metadata, not model claims. They are outside the unchanged canonical finding schema and never count as checkpoint evidence. Python metrics travel with each result rather than through a shared mutable last-result field. Existing admission/completion timestamps, frame IDs/hashes and context remain authoritative.

## Compact-output experiment: rejected

A bounded live trial used Gemini 3.5 Flash-Lite, the same four labelled controlled screenshots, checkpoint/procedure context and 2,600-token budget. The baseline v3 prompt and ID-bearing JSON passed all four focused checks. An initial compact positional c/a/s/u format reduced generated output to 250–326 tokens versus 451–464, but failed wrong-settings, Carrier-vs-Local action and obscured-wire acceptance. A second compact format retained stable authored IDs and passed three of four; it still claimed occluded receiver wiring matched. It was rejected too. Neither compact prompt/decoder is deployed. The original dsb-step-observer/v3 and ID-bearing JSON schema remain in production.

These results do not imply TOON itself has that failure; TOON was not tested. They establish that reducing representation and changing the observer contract needs held-out semantic checks, not merely byte-count or parse checks. The trials show no reliable model-latency improvement: baseline times were 9.66/2.54/4.07/4.15 s; final compact-ID times 4.40/7.07/4.50/6.13 s. Their medians are approximately 4.11 and 5.32 s. Interleaving/order, cache behavior, stochastic findings and provider load confound timing. Each case had one call per format; no general performance inference is justified.

Safe reports are committed in the Site under docs/evidence/2026-10-14-latency-format-trial.json and docs/evidence/2026-10-14-latency-stable-id-trial.json. Root artifacts: work/latency-eval/report.json and work/latency-eval-stable-ids/report.json, prompt hashes and controlled image hashes included. No user lab was mutated by the twelve test calls. scripts/compare-latency-formats.py uses the archived trial request template for any deliberate later rerun; no more paid calls are needed for this change.

## Streaming and next experiments

Frame provenance is generated before/around inference by the trusted runtime; the model does not currently generate or stream it. Partial output can improve perceived responsiveness, but cannot become admitted checkpoint evidence until relevant IDs, status/evidence, complete response termination and current context are validated. Final mismatch/uncertainty, truncation, a stale view/visit or cancellation must not leave a prematurely completed checkpoint. Rendering still never completes a checkpoint.

The next high-value model experiment is focused current-action verification with a smaller relevant context and explicit unknowns for unrequested targets, while retaining authored IDs and complete evidence. Then compare structured-JSON streaming and TOON with complete-field parsing, cancellation/context checks and provisional UI states. A safe implementation can stream “checking” and provisional findings before a final validated commit. Final advancement continues to require two distinct admitted observations. TOON's uniform-table token savings and Gemini's schema-constrained JSON support are different capabilities; neither implies lower end-to-end latency by itself.
