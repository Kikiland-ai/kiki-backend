This version targets the existing private receiver at https://kiki-screen-receiver.woodsycarp256.chatgpt.site. It combines producer `1c658b6` with the independent 0.4.0 renderer on `integration/analysis-owned-guidance`; the latency comparison Site and PR #1 are unchanged. The analysis call supplies drawing intent; the consumer validates current source/context and paints it on the connected live MATLAB tab. No second localization/model call runs in the extension.

Use adapter 0.4.0, connect the MATLAB tab to this receiver, share that same browser tab, then start the guided lab. The connection button negotiates source identity and versions; it does not draw a fixed sample. Capture, analysis and delivery status are separate, with bounded diagnostics in Annotation trace.

Worker D1 batch persistence assigns ordered cancellation/cue sequences atomically with outbox insertion and guards lab revisions. Signed actual paint ACKs record exposure only. Existing tracker rules remain authoritative. Preserve all existing secrets and D1 rows; migration 0004 appends guidance tables after the existing 0003 migration.

## Python cloud bridge

After a verified Python deployment, configure server-only `KIKI_FASTAPI_ORIGIN` and `KIKI_PROXY_SECRET` through Sites runtime settings. This switches the private page, capture HTTP/WebSocket routes and MCP reads to Python. Without a Python origin, the existing Worker demo continues. A configured unreachable backend fails visibly; it never falls back to a different progress store. Earlier D1 lab data is preserved; it is not automatically migrated to the Python projection. No external Python hosting or Render resource is created by publishing this adapter.

Five new controlled edge checks pass alongside the previous twenty-one checks. A synthetic WebSocket handshake checks forwarding only; actual Sites-to-Python WebSocket acceptance is a separate deployment test.

A private HTTPS capture page and thin Cloudflare Worker receiver, built because this ChatGPT interface has no verified cloud port-preview control. It complements the FastAPI receiver in Kikiland-ai/kiki-backend rather than replacing the chosen backend framework.

Open the deployed Site in a separate desktop-browser tab, sign in with the owning ChatGPT account, click Share screen and select a tab/window/screen. The browser sends JPEGs up to once every two seconds to POST /screen-sessions/{id}/frame; the server returns the actual received bytes. The receiver pane displays that response image and server-generated receipt metadata. Pause/resume/stop are serialized with uploads.

Sampling waits two seconds after each upload completes, avoiding catch-up bursts when the browser's timers are delayed. A specifically identified sampling-rate 429 includes Retry-After/retry_after_ms; the client waits with capture still active. Authentication/invalid-input errors, session expiry and other terminal errors remain visible and stop the trial. The session still has its 30-minute cap.

There is no raw image or video archive, D1 database or R2 bucket. The Worker signs short-lived receipt state using the secret CAPTURE_RECEIPT_KEY configured through Sites runtime environment variables. The browser keeps the current receipt in an HTTP-only, secure, same-site cookie and frame/receipt history in page memory. GET /screen-sessions/{id}/observation verifies that receipt and computes freshness. Stop records an ended receipt in the browser; this stateless demo does not offer global replay revocation, a durable shared session journal, device handoff or production job coordination. Raw pixels are visible only in the current browser response/preview.

Private Sites dispatch gates entry and supplies authenticated user identity. APIs require that identity, match the receipt owner and reject cross-origin mutations. Local QA simulates identity only on a loopback dev server. It does not prove a deployed visitor's sign-in flow.

The server validates metadata bounds, byte count, JPEG envelope/dimensions and monotonic sequence/capture time. A decoded browser image verifies display; Worker envelope checking is not a general image-decoder/scientific validator. Receipt hashes are calculated from actual received bytes. Frames are capped at 1 MB/max dimension 1600 px, sessions at 30 minutes, with 1,000 receipts per signed session. One normal UI session has one in-flight upload. Independent replay/fork protection is future durable-state work.

## Selected-frame analysis

The user authorized reusing the environment's Gemini key as a server-side Site secret. GEMINI_API_KEY is configured through native Sites environment variables; the browser never receives it. The default vision model is gemini-3.5-flash-lite, with minimal thinking and bounded JSON output. The current rotation/failover behavior is documented below and in docs/key-rotation-and-model-comparison.md.

After receiving a frame, the browser independently sends its exact returned JPEG plus metadata to POST /screen-sessions/{id}/analyze. The server verifies it against the current signed capture receipt before calling Gemini. The normal page allows one browser analysis request at a time, no more than one start per 10 seconds and 30 starts per page session, including failed browser requests. The server also enforces a cooperative signed-receipt count/interval. These are trial controls, not a durable global quota: replay/forking cookies and aborted requests require a future shared coordinator. Frame uploads do not await the model.

The model returns summary, up to three visible facts, a comparison with the previous REPORT and explicit uncertainties. Screenshots and previous report text are untrusted data; the system prompt restricts interpretation to visible evidence and treats changes as reported-state comparisons. Runtime output validation checks shape/size, not factual truth or comprehensive prompt-injection resistance. The runtime, rather than the model, supplies IDs, source-frame hash/sequence/capture time/receipt time, completion time, model and prompt version.

GET /screen-sessions/{id}/observation now returns screen-awareness/v1 after a successful analysis. observation.source_frame is the image actually analyzed; observation.latest_frame is the newest received frame, which may be newer. analysis.age_ms measures source-frame age and stale becomes true above 20 seconds. Each fact references its evidence frame. A separate signed HTTP-only analysis cookie means a late model result cannot roll back capture count or lifecycle state. Provider/schema failures preserve the last successful result, label it failed/stale as appropriate, and keep capture active. Pause stops new sampling/analysis; an already-running request can finish. Stop aborts the browser request and ignores late results; it does not guarantee canceling work already started at Gemini.

Only the latest bounded report is in signed cookie state. The page keeps receipt/observation events in memory until it is closed/restarted; there is no durable cloud observation history or retained screenshot evidence. Hashes establish input identity but cannot reconstruct archived pixels. Gemini's provider-side processing/retention is separate from the receiver's no-image-archive behavior. FastAPI analysis integration, durable event/evidence retention, adaptive candidate selection, action planning and graphics remain subsequent work.

## Continuous sessions and quota recovery (14 October 2026)

This section supersedes the historical 30-read, 30-minute, 1,000-frame, eight-run, 500-event and 100-response rejection caps above. They are removed. Per-frame size/provenance checks, one upload in flight and minimum analysis cadence remain. Native sharing, saved place and event history continue while provider analysis waits, and the browser automatically retries a new fresh frame after cooldown. Transient capture 429/5xx/network failures also wait without stopping the shared track.

Provider configuration supports the existing server-only GEMINI_API_KEY, or GEMINI_API_KEYS as a JSON array of {key,quota_pool}. Each quota_pool must identify an actual independent Google project/model quota pool; keys in the same pool are never cycled on 429. Labels are administrator declarations, not Google-verified identities. At most two independent available pools can be attempted under one twenty-second frame deadline. Cooldowns honor Retry-After (seconds or date) and persist in D1 via drizzle/0001_provider_cooldowns.sql. Default 429 wait is sixty seconds; network/5xx ten seconds, exponential up to five minutes; longer provider Retry-After wins. Nonretryable configuration/authentication failures get fifteen-minute recovery spacing. No key or provider body is returned to the browser. This is cooldown coordination, not a distributed admission/lease scheduler.

Journal GET now pages ordered events with ?after=0&limit=100. Full lab export fetches successive pages. Recent responses in the state/model context are a window of 100 per kind; full new records and IDs remain in the durable journal. Ordinary sampled images are not archived; only the latest checked lab image is retained. Historical runs and existing evidence are preserved. The private UI/MCP run list returns recent runs; it does not prevent more runs or continuing an older owned ID. Storage, provider quotas and browser/hosting availability are finite, so this guarantees removal of artificial counters and recovery behavior, not infinite infrastructure.

Verified with controlled provider failures, both backend suites and native tab-sharing QA; no real Google quota was exhausted for testing. The Worker remains the hosted compatibility backend until the separate FastAPI origin is deployed and configured.

## Key rotation and model comparison (14 October 2026)

The [rotation guide](docs/key-rotation-and-model-comparison.md) supersedes the earlier two-independent-pool and 5xx exponential selection policy. The router reserves a durable last-used-key cursor and lease, rotates distinct credentials on each outbound attempt, tries the next eligible key immediately on 503/network failure, and waits at least sixty seconds after a failed full sweep. Healthy cycles have no artificial wait. Same-project keys still share 429 cooldowns; longer Retry-After is honored. At least two distinct configured keys are required for nonconsecutive reuse. With several configured keys and only the last one eligible, the router waits for an alternative. Cursor/cooldown survive Worker restarts through the appended D1 migration; no lab history is reset.

Set **Site runtime secret GEMINI_API_KEYS** to a JSON list such as `["REPLACE_WITH_KEY_1","REPLACE_WITH_KEY_2","REPLACE_WITH_KEY_3"]`, save and redeploy the current Site version. Existing GEMINI_API_KEY remains supported when no list exists. Optional {key,quota_pool} entries identify actual Google projects; keys in one project do not expand quota. Coding-environment variables and Site production variables are separate. GET /health returns key count, configuration validity and selected model names without keys. No extra real keys have been installed by this implementation.

The default is now gemini-3.5-flash-lite; GEMINI_LAB_MODEL can override lab checks and GEMINI_SCREEN_MODEL generic observation. A controlled nine-call comparison found three 503s on 3.1 Lite, three successful expected focused findings on 3.5 Lite, and two 503s plus one timeout on 3.8 Flash. [Safe raw results](docs/evidence/2026-10-14-model-comparison.json). This small cloud-runtime test is not proof of general uptime, deployed Site egress or real Simulink accuracy.
